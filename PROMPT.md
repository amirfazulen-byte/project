Ты — опытный Python-разработчик. Сделай веб-сайт «Свободно?» строго по этому описанию. Описание подробное специально: если что-то в нём указано точно (название поля, текст сообщения, формат времени, имя файла), делай именно так. ## 1. Суть проекта

**Проблема.** В школьных интернатах жильцы делят общие ресурсы: стиральные машины, комнаты для самоподготовки, спортзал. Очередь держится на чатах и бумажках, отсюда споры и пропуски.

**Решение.** Сайт, на котором ученик с телефона за несколько секунд находит свободное время у нужного ресурса и бронирует его одним нажатием. Воспитатель настраивает ресурсы и видит все брони. Владелец сайта подключает новые интернаты.

**Главная функция:** ученик открывает сайт → сразу видит расписание → выбирает ресурс и день → нажимает на свободный слот → бронь готова. Всё должно быть удобно с телефона.

Сайт делается для конкурса по технологическому предпринимательству, поэтому он должен быть простым, надёжным и хорошо смотреться на демонстрации.

## 2. Роли и права

Сайт поддерживает **несколько интернатов**. У каждого интерната свои ресурсы, жильцы, воспитатели и свой код для регистрации жильцов.

| Роль | Что может | Как входит |
|---|---|---|
| **Ученик** (`student`) | Смотрит расписание своего интерната, бронирует свободные слоты, видит свои брони и отменяет свои будущие брони | Код интерната + имя + номер комнаты + пароль |
| **Воспитатель** (`warden`) | В своём интернате: добавляет и меняет ресурсы, ставит ресурс «на ремонт», видит все брони на любой день, отменяет любую бронь, видит и меняет код интерната | Логин + пароль |
| **Владелец сайта** (`owner`) | Создаёт интернаты, создаёт аккаунты воспитателей, видит заявки на подключение с главной страницы. Не привязан ни к одному интернату | Логин + пароль |
| **Гость** (не вошёл) | Видит главную страницу, отправляет заявку «Подключить интернат», регистрируется, входит | — |

Строгое правило: **воспитатель и ученик никогда не видят и не меняют данные чужого интерната.** Каждый запрос к базе от их имени фильтруется по `school_id` текущего пользователя.

## 3. Технологии и ограничения

- **Python 3.10+**, **Flask 3**, **SQLite** через стандартный модуль `sqlite3` (без SQLAlchemy и других ORM).
- Шаблоны **Jinja2** (встроены во Flask), автоэкранирование включено (файлы `.html`).
- **Обычный CSS** в одном файле, без фреймворков (без Bootstrap, Tailwind и т. п.), без сборщиков, без npm.
- JavaScript почти не нужен. Единственное допустимое использование — `onsubmit="return confirm('...')"` для подтверждения опасных действий. Никаких JS-библиотек.
- Пароли хранить **только как хэш**: `werkzeug.security.generate_password_hash` / `check_password_hash` (Werkzeug ставится вместе с Flask).
- Защиту форм от CSRF сделать **вручную** (без Flask-WTF), см. раздел 7.
- **Часовой пояс — московский** (`Europe/Moscow`) через стандартный `zoneinfo`.
- Файл `requirements.txt` — ровно две строки:
  ```
  Flask>=3.0
  tzdata
  ```
  (`tzdata` нужен, чтобы `zoneinfo` работал на Windows.)
- Интерфейс полностью **на русском языке**.
- Из личных данных жильцов хранить **только имя и номер комнаты**. Никаких телефонов, почты, фамилий отдельно, дат рождения.
- Не добавляй функций сверх описанных (никаких уведомлений, почты, удаления аккаунтов, сброса пароля, API, тёмной темы и т. п.) без моего согласия.

## 6. База данных (`app/schema.sql`)

Используй именно эту схему (скрипт сначала удаляет таблицы — команда `init-db` создаёт базу с нуля):

```sql
DROP TABLE IF EXISTS bookings;
DROP TABLE IF EXISTS resources;
DROP TABLE IF EXISTS users;
DROP TABLE IF EXISTS schools;
DROP TABLE IF EXISTS requests;

CREATE TABLE schools (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  code TEXT NOT NULL UNIQUE
);

-- У владельца school_id пустой. Логин есть у воспитателей и владельца,
-- ученик входит по коду интерната, имени и комнате.
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  school_id INTEGER REFERENCES schools(id) ON DELETE CASCADE,
  role TEXT NOT NULL CHECK (role IN ('student', 'warden', 'owner')),
  name TEXT NOT NULL,
  room TEXT,
  login TEXT UNIQUE,
  password_hash TEXT NOT NULL
);
CREATE UNIQUE INDEX students_unique ON users (school_id, name, room) WHERE role = 'student';

CREATE TABLE resources (
  id INTEGER PRIMARY KEY,
  school_id INTEGER NOT NULL REFERENCES schools(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  slot_minutes INTEGER NOT NULL CHECK (slot_minutes > 0),
  open_time TEXT NOT NULL,   -- 'ЧЧ:ММ'
  close_time TEXT NOT NULL,  -- 'ЧЧ:ММ'
  weekly_limit INTEGER NOT NULL DEFAULT 3 CHECK (weekly_limit > 0),
  is_broken INTEGER NOT NULL DEFAULT 0
);

-- start_at — московское время 'ГГГГ-ММ-ДД ЧЧ:ММ'. UNIQUE не даёт занять слот дважды.
CREATE TABLE bookings (
  id INTEGER PRIMARY KEY,
  resource_id INTEGER NOT NULL REFERENCES resources(id) ON DELETE CASCADE,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  start_at TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (resource_id, start_at)
);

CREATE TABLE requests (
  id INTEGER PRIMARY KEY,
  school_name TEXT NOT NULL,
  contact_name TEXT NOT NULL,
  contact TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Важные детали:
- Подключение (`db.get_db()`): `sqlite3.connect(...)`, `row_factory = sqlite3.Row`, сразу `PRAGMA foreign_keys = ON`. Соединение хранится в `flask.g` и закрывается в `teardown_appcontext`.
- **Отмена брони = удаление строки** из `bookings`. Тогда слот снова свободен, а `UNIQUE (resource_id, start_at)` продолжает работать.
- **Код интерната**: 6 случайных символов из алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (без похожих I, O, 0, 1), через модуль `secrets`. Функция `new_school_code()` в `db.py` генерирует код, пока не найдёт такой, которого нет в базе.
- `requests.created_at` при вставке заполнять **явно московским временем** в формате `ГГГГ-ММ-ДД ЧЧ:ММ` (не полагаться на `CURRENT_TIMESTAMP`, он в UTC).

## 7. Вход, сессии, CSRF (`app/auth.py`)

Блюпринт `auth` без префикса.

**Загрузка пользователя и проверка CSRF** — одна функция с `@bp.before_app_request`:
1. Берёт `user_id` из `session`, загружает строку из `users` в `g.user` (или `None`).
2. Если метод запроса `POST`: берёт токен `session["csrf"]`; если токена нет или `request.form["csrf"]` с ним не совпадает — `abort(400)`.

**Выдача токена** — `@bp.app_context_processor`: если в сессии нет `csrf`, кладёт туда `secrets.token_hex(16)`; возвращает `{"csrf": session["csrf"]}`. В **каждой** POST-форме сайта есть поле `<input type="hidden" name="csrf" value="{{ csrf }}">`.

**Декоратор `role_required(*roles)`**: если `g.user` нет — редирект на `auth.login`; если роль не входит в `roles` — `abort(403)`.

**Куда вести после входа** — словарь:
```python
HOME = {"student": "student.schedule", "warden": "warden.panel", "owner": "owner.panel"}
```

**Функция входа `log_in(user)`**: `session.clear()`, `session.permanent = True`, `session["user_id"] = user["id"]`, редирект на `HOME[роль]`. (После `session.clear()` старый CSRF-токен пропадает, новый выдаётся на следующей странице — это нормально.)

**Маршруты:**

| URL | Методы | Что делает |
|---|---|---|
| `/register` | GET, POST | Регистрация ученика. Поля: код интерната, имя, комната, пароль |
| `/login` | GET, POST | Вход ученика. Те же 4 поля |
| `/staff` | GET, POST | Вход воспитателя или владельца: логин и пароль |
| `/logout` | POST | `session.clear()`, редирект на главную (`owner.index`) |

Выход — только POST (кнопка-форма в шапке), не ссылка.

**Обработка полей ученика** (общая функция для `/register` и `/login`): код — `strip().upper()` (регистр не важен), имя и комната — `strip()`, пароль — как есть.

**Регистрация `/register` (POST)**, проверки по порядку:
1. Нет интерната с таким кодом → сообщение «Неверный код интерната.»
2. Пустое имя, пустая комната или пароль короче 4 символов → «Заполните имя и комнату, пароль — от 4 символов.»
3. Вставка в `users` с ролью `student`. Если сработал уникальный индекс (`sqlite3.IntegrityError`) → «Жилец с таким именем и комнатой уже зарегистрирован.»
4. Успех → сразу вход (`log_in`) → страница «Расписание».

**Вход ученика `/login` (POST)**: ищет пользователя через JOIN `users` + `schools` по `code`, `role = 'student'`, `name`, `room`; проверяет хэш пароля. Ошибка → «Неверные данные для входа.» (не уточнять, что именно неверно).

**Вход персонала `/staff` (POST)**: ищет по `login` (после `strip()`) среди ролей `warden` и `owner`, проверяет пароль. Ошибка → «Неверный логин или пароль.»

При ошибках формы введённые значения (кроме пароля) остаются в полях: `value="{{ request.form.code }}"` и т. п.

## 8. Время

- Вся работа со временем — в **московском времени без часового пояса** (naive datetime). Текущее время: `datetime.now(TZ).replace(tzinfo=None)` — функция `slots.now()`.
- В базе время слота хранится строкой формата `FMT = "%Y-%m-%d %H:%M"`, например `2026-10-22 07:00`. Такие строки правильно сравниваются как обычные строки (`<`, `>`, `LIKE '2026-10-22%'`), это используется в запросах.
- Время работы ресурса — строки `ЧЧ:ММ`; функция `minutes("07:30") → 450`.

## 9. Правила бронирования (`app/slots.py`)

Константы: `FMT = "%Y-%m-%d %H:%M"`, `DAYS_AHEAD = 7`.

**Сетка слотов дня** — `day_slots(resource, day)`: начинаем с `open_time`, шаг `slot_minutes`; слот добавляется, только если он **целиком заканчивается не позже** `close_time` (`t + шаг <= закрытие`). Пример: спортзал 08:00–21:00 по 90 минут → 08:00, 09:30, 11:00, 12:30, 14:00, 15:30, 17:00, 18:30 (слот 20:00 не помещается). Стирка 07:00–22:00 по 60 минут → 07:00 … 21:00 (15 слотов).

**Дни для выбора** — `booking_days()`: сегодня и ещё 7 дней (всего 8 дней).

**Окно бронирования** — `in_window(start)`: `сейчас < start <= сейчас + 7 дней`. То есть нельзя бронировать прошедшее (и уже начавшееся) время и дальше чем на 7 суток вперёд.

**Функция `book(db, user, resource, start)`** возвращает текст ошибки или `None` при успехе. Проверки строго в таком порядке:
1. Ресурс на ремонте (`is_broken`) → «Ресурс на ремонте, бронировать нельзя.»
2. `start` не входит в сетку `day_slots` этого дня → «Такого слота нет.»
3. Не проходит `in_window` → «Можно бронировать только будущее время и не дальше чем на 7 дней.»
4. Дальше — **одна транзакция** `db.execute("BEGIN IMMEDIATE")` (блокирует запись, чтобы два одновременных запроса не обошли лимит):
   - считаем брони этого пользователя на этот ресурс в **календарной неделе слота** (с понедельника 00:00 до следующего понедельника): `start_at >= 'дата понедельника' AND start_at < 'дата следующего понедельника'`. Считаются все брони недели, включая уже прошедшие;
   - если количество `>= weekly_limit` → `rollback` и «Лимит исчерпан: не больше N броней в неделю на «Название».»
   - иначе `INSERT` в `bookings` и `commit`;
   - если `INSERT` упал с `sqlite3.IntegrityError` (кто-то успел занять этот слот) → `rollback` и «Этот слот уже заняли.»

Так **один слот физически нельзя занять дважды** даже при одновременных нажатиях: это гарантирует `UNIQUE (resource_id, start_at)` в базе, а не проверка в Python.

**Защита сетки.** Если воспитатель меняет длительность слота или время открытия, сетка сдвигается, и старые брони перестают совпадать со слотами — появляется возможность пересекающихся броней. Поэтому менять `slot_minutes` и `open_time` у ресурса **запрещено, пока у него есть брони с сегодняшнего дня и позже** (`start_at >= 'сегодняшняя дата'`). Сообщение: «Длительность слота и время открытия нельзя менять, пока есть брони с сегодняшнего дня. Сначала отмените их.» Название, время закрытия и лимит менять можно всегда.

## 10. Страницы ученика (`app/student.py`)

Блюпринт `student` без префикса. Все маршруты — `@role_required("student")`.

**Фильтры шаблонов** (регистрируются через `@bp.app_template_filter`, доступны во всех шаблонах):
- `day_label(date)` → «Сегодня», «Завтра», иначе «ср, 23.10» (дни недели: пн, вт, ср, чт, пт, сб, вс).
- `slot_label("2026-10-22 07:00")` → «Завтра, 07:00» (день через `day_label` + время).

### `/schedule` — Расписание (GET)
Параметры: `r` — id ресурса, `d` — дата `ГГГГ-ММ-ДД`.
- Ресурсы — только интерната ученика, по алфавиту.
- Если `d` не дата или не входит в `booking_days()` → сегодня. Если `r` не найден среди ресурсов интерната → первый ресурс.
- Если ресурсов нет: «В интернате пока нет ресурсов. Попросите воспитателя их добавить.»
- Вверху два ряда «чипсов» (кнопки-ссылки, ряд прокручивается вбок на телефоне):
  1. ресурсы (выбранный подсвечен);
  2. 8 дней с подписями `day_label` (выбранный подсвечен).
  Переключение сохраняет второй параметр (при смене ресурса остаётся тот же день и наоборот).
- Если ресурс на ремонте — жёлтая плашка ««Название» на ремонте, бронировать нельзя.»
- Ниже — сетка слотов дня. У каждого слота время `ЧЧ:ММ` крупно и подпись мелко. Состояния:
  - **занят мной** → «моё» (залитая зелёная плитка);
  - **занят другим** → «занято» (серая плитка; кто занял, ученикам **не показывать**);
  - ресурс на ремонте или слот вне окна бронирования → «недоступно» (полупрозрачная);
  - иначе **«свободно»** — это кнопка, нажатие сразу бронирует (форма POST на `/book` со скрытыми полями `csrf`, `resource`, `start`). **Бронь в одно нажатие, без подтверждений.**
  Занятость определяется одним запросом: брони ресурса за день (`start_at LIKE 'ГГГГ-ММ-ДД%'`) → словарь `start_at → user_id`.

### `/book` — Забронировать (POST)
- Ресурс ищется по `id` **и** `school_id` ученика; `start` разбирается по `FMT`. Если ресурс не найден или время не разобралось → `abort(400)`.
- Вызывает `slots.book(...)`. Сообщение: ошибка из `book` или «Готово: Название, Завтра, 07:00.»
- Редирект обратно на `/schedule?r=<ресурс>&d=<день слота>`.

### `/my` — Мои брони (GET)
- Брони ученика с `start_at >= сегодняшняя дата` (сегодняшние, включая уже прошедшие сегодня, и будущие), по времени. Строка: **название ресурса** жирным, ниже `slot_label`.
- Кнопка «Отменить» показывается только у броней, которые ещё не начались (`start_at > текущее время в формате FMT`).
- Пусто → «Броней нет.» и ссылка «Открыть расписание».

### `/my/<id>/cancel` — Отмена (POST)
`DELETE FROM bookings WHERE id = ? AND user_id = <я> AND start_at > <сейчас>`. Если удалилась строка — «Бронь отменена.», иначе «Эту бронь уже нельзя отменить.» (в т. ч. при попытке отменить чужую). Редирект на `/my`.

## 11. Панель воспитателя (`app/warden.py`)

Блюпринт `warden` с префиксом `/warden`. Все маршруты — `@role_required("warden")`. Вспомогательная функция `get_resource(id)` ищет ресурс по `id` **и** `school_id` воспитателя, иначе `abort(404)`.

### `/warden/` — Ресурсы и код (GET)
- Заголовок — название интерната.
- Карточка: «Код для регистрации жильцов: **КОД**» (крупно, с разрядкой) и кнопка-ссылка «Сменить код» с подтверждением `confirm('Сменить код? Жильцы будут входить и регистрироваться с новым кодом.')`.
- Раздел «Ресурсы»: кнопка «Добавить ресурс»; список ресурсов по алфавиту. В строке: название (если на ремонте — красная метка «на ремонте»), ниже мелко «60 мин, 07:00–22:00, до 3 в неделю». Справа: ссылка «Изменить» и кнопка «На ремонт» / «Починили».
- Нет ресурсов → «Ресурсов пока нет.»

### `/warden/code` (POST) — Сменить код
Новый код через `new_school_code()`, сообщение «Новый код интерната: КОД». Аккаунты жильцов не меняются, но входить и регистрироваться они теперь будут с новым кодом.

### `/warden/resource/new` и `/warden/resource/<id>` (GET, POST) — Форма ресурса
Одна функция на оба адреса. Поля:
- «Название» (`name`, placeholder «Стиралка 1»);
- «Длительность слота, минут» (`slot_minutes`, number);
- «Открытие» и «Закрытие» (`open_time`, `close_time`, `<input type="time">`);
- «Броней в неделю на человека» (`weekly_limit`, number).

Значения по умолчанию для нового: 60 минут, 07:00, 22:00, лимит 3.

Проверки (по порядку, сообщение — первая не прошедшая):
1. Время разбирается по `%H:%M` (и нормализуется обратно в `ЧЧ:ММ`) → иначе «Укажите часы работы в формате ЧЧ:ММ.»
2. Название не пустое → «Введите название.»
3. `5 <= slot_minutes <= 720` → «Длительность слота — от 5 до 720 минут.»
4. `1 <= weekly_limit <= 50` → «Лимит в неделю — от 1 до 50.»
5. `открытие + длительность <= закрытие` (помещается хотя бы один слот) → «Закрытие должно быть позже открытия хотя бы на один слот.»
6. Защита сетки из раздела 9 (только при изменении существующего ресурса).

При ошибке форма показывается снова с введёнными значениями. Успех → «Сохранено: Название.» и редирект на `/warden/`. Кнопки: «Сохранить» и ссылка «Отмена». **Удаления ресурсов нет** (его нет в задании).

### `/warden/resource/<id>/repair` (POST) — Ремонт
Переключает `is_broken`. Сообщения: ««Название» на ремонте, новые брони закрыты.» / ««Название» снова работает.» **Уже сделанные брони при этом не отменяются** — воспитатель отменяет их вручную, если нужно.

### `/warden/bookings` (GET) — Брони на день
- Параметр `d`; если не дата — сегодня. Любой день (и прошлый тоже).
- Заголовок «Брони: Сегодня» (через `day_label`), форма выбора даты `<input type="date">` + кнопка «Показать».
- Список всех броней интерната за день по времени: **время** жирным · ресурс, ниже мелко «Имя, комната N». Кнопка «Отменить» с подтверждением `confirm('Отменить эту бронь?')`.
- **Важно для безопасности:** не вставляй имя жильца внутрь JavaScript (`confirm('... {{ имя }}')`): имя с апострофом сломает скрипт и откроет XSS. Текст подтверждения — без пользовательских данных.
- Пусто → «В этот день броней нет.»

### `/warden/bookings/<id>/cancel` (POST)
`DELETE ... WHERE id = ? AND resource_id IN (SELECT id FROM resources WHERE school_id = <мой интернат>)`. «Бронь отменена.» или «Бронь не найдена.» Скрытое поле `d` в форме — чтобы вернуться на тот же день.

Блюпринт `owner` без префикса.

### `/` — Главная (GET, POST)
- Если пользователь уже вошёл и открывает главную (GET) — сразу редирект в его раздел (`HOME[роль]`): ученику так быстрее попасть в расписание.
- Содержимое для гостя (`<title>`: «Бронирование в интернате — Свободно?»):
  1. Крупный заголовок «Свободно?» и подзаголовок: «Запись в стиралку, комнату для самоподготовки и спортзал интерната — с телефона за несколько секунд.» Кнопки «Войти» (залитая) и «Регистрация» (контурная). Ссылка «Подключить свой интернат» (якорь `#connect`).
  2. «Как это работает» — нумерованный список:
     - Воспитатель добавляет ресурсы и часы работы и сообщает жильцам код интерната.
     - Жилец регистрируется по коду, открывает расписание и видит свободное время.

  3. «Чем полезно интернату»:

  4. «Подключить интернат» (`id="connect"`) — форма: «Название интерната» (`school_name`), «Ваше имя» (`contact_name`), «Телефон или e-mail» (`contact`), все обязательные, `maxlength="200"`, кнопка «Отправить заявку».
- POST: все три поля после `strip()` не пустые и не длиннее 200 символов, иначе «Заполните все поля заявки.» (форма показывается снова с введёнными значениями). Успех → запись в `requests` (с `created_at` по Москве), сообщение «Спасибо! Заявка отправлена, мы свяжемся с вами.», редирект на `/`.

### `/owner/` — Панель владельца (GET, `@role_required("owner")`)
Три раздела в таком порядке:
1. **«Интернаты»**: форма «Название» + «Создать интернат»; список по алфавиту: название, ниже «жильцов: N» (число учеников), справа код крупно. Пусто → «Интернатов пока нет.»
2. **«Воспитатели»**: форма (показывается, только если есть хотя бы один интернат): «Интернат» (выпадающий список), «Имя», «Логин», «Пароль (от 6 символов)» — поле пароля обычное текстовое (`autocomplete="off"`), чтобы владелец видел, что передаёт воспитателю; кнопка «Создать воспитателя». Список: имя, ниже «Интернат · логин vos». Пусто → «Воспитателей пока нет.»
3. **«Заявки с главной»**: новые сверху: название интерната, ниже «Имя · контакт · Сегодня, 14:05». Пусто → «Заявок пока нет.»

### `/owner/schools` (POST)
Пустое название → «Введите название интерната.» Иначе создать с `new_school_code()` → «Интернат «Название» создан, код: КОД». Редирект на `/owner/`.

### `/owner/wardens` (POST)
- Интернат (`school`, id) должен существовать, имя и логин не пустые → иначе «Выберите интернат и заполните имя и логин.»
- Пароль короче 6 → «Пароль воспитателя — от 6 символов.»
- Логин занят (`IntegrityError`) → «Такой логин уже занят.»
- Успех → «Воспитатель Имя создан, логин: vos». Редирект на `/owner/`.

## 16. Безопасность — чек-лист

- Пароли только хэшем; минимальная длина: ученик 4, воспитатель 6.
- Во всех POST-формах есть CSRF-токен; POST без токена → 400.
- Все SQL-запросы — с параметрами `?`, никакой склейки строк с пользовательскими данными.
- Все запросы ученика и воспитателя ограничены их `school_id`; чужой ресурс → 400 (бронь) или 404 (панель воспитателя); чужая роль → 403.
- Автоэкранирование Jinja не отключать; `|safe` не использовать; пользовательские данные не вставлять в JavaScript.
- Выход — только POST.
- На сервере задать `SECRET_KEY` через переменную окружения.

## 17. Как проверить (критерии приёмки)

Проверь каждый пункт сам (например, через `app.test_client()` во Flask) и покажи мне результат:

3. Ученик не открывает `/warden/` и `/owner/` (403); после выхода `/schedule` ведёт на вход.

9. Ресурс «на ремонте» → бронь запрещена, в расписании плашка и «недоступно».
10. Воспитатель: добавление и изменение ресурса, все ошибки формы, ремонт, список броней дня с именем и комнатой, отмена; чужой воспитатель получает 404 и не видит чужие брони.

12. Смена кода: со старым кодом войти нельзя, с новым — можно, аккаунт тот же.

14. Владелец создаёт интернат (появляется код) и воспитателя; дубль логина и короткий пароль — ошибки; новый воспитатель входит и видит свой интернат.
15. Вошедший пользователь на `/` перенаправляется в свой раздел.
16. На ширине экрана 360px нет горизонтальной прокрутки, слоты нажимаются пальцем.
